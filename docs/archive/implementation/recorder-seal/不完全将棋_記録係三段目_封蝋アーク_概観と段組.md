## 0. なぜこのアークか

記録は「誰でも書ける JSON」のままだと、後から書き換えられても誰も気づけない。二証人は**対局者どうしの食い違い**を検知するが、**綴じた後の改竄**は検知しない。封蝋はその穴を塞ぐ。

そして今、これを先にやる実利がある——**テストプレイを AI で量産するアークがこの後に続く**（バックログ §E）。量産したログを後で分析するとき、「このデータは確かに当時綴じられたもので、後から触っていない」が機械検証できるかどうかで、データの意味が変わる。**信頼できる器を先に作ってから、大量に流し込む。**

### 0.1 封蝋が塞ぐ穴・塞がない穴（正直に）

過大な期待を書かない。封蝋が実際に与える保証はこれだけ:

- **塞ぐ**: 鍵を持たない者による改竄。content-address と組み合わさると相当強い——`text` を書き換えれば SHA-256 が KV キー（`id`）と合わず、辻褄を合わせようと再署名しても、やはりキーと合わない。**第三者が、書庫を運営する者の言葉を信じずに、独立して完全性を確かめられる**ようになる。これが本体。
- **塞がない**: (a) **削除**——記録ごと消されれば封蝋は何も言わない。(b) **鍵を持つ運営者による捏造**——鍵があれば、ありもしない対局を封じられる。

(b) の第一の防波堤は**二証人**（対局者二人の独立した目が一致して初めて確定綴じ）であり、究極的には**複数記録係の突き合わせ**（二段目 §13・版図の遠い地平）。封蝋はそれを置き換えるものではなく、その上に重ねる一層である。**§14-3「署名は二証人の上に乗る層で、土台ではない」は、この意味でも読まれること。**

## 1. 何を封じ、何を封じないか（淀川 §1.4 の線を厳守）

**封じるのは中身の完全性だけ。** 記録係は対局の当事者ではない（権威なき観察者）。だから署名は中身に混ぜず、丸ごとエンベロープに置く。そして担保するのは「**記録係が自分で観察した事実**」に限る:

| 封じる（記録係が観察した） | 封じない（記録係の領分でない） |
|---|---|
| `id` ＝ 正準本文の SHA-256（＝中身そのもの） | 帰属（誰の棋譜か）＝ principal と場の領分 |
| `witnesses` ＝ 何人の証言が揃ったか | consent receipt 参照・法的根拠 ＝ principal 自身の領分 |
| `archived_at` ＝ いつ綴じたか | どちらの証言が正しいか ＝ **裁定しない**（審判なし） |
| `kid` ＝ どの鍵で封じたか | 対局者各々の署名（淀川 §1.4 で保留のまま・触らない） |

> **二段目 §14-2「審判なし」に忠実であること。** disputed を封じるのは「両言い分をこう受け取った」という**受領の事実**を封じるのであって、どちらかを正しいと述べるのではない。statement は `text_a`/`text_b` を**並置**するだけで、優劣を含む語（`correct` 等）を持たない。

## 2. 封蝋の書式（engine のアーカイブ書式に倣った行ベース）

正準化は `engine/src/archive.rs::kifu_to_archive` と同じ**行ベース・`\n` join・末尾改行なし**に揃える。JSON 正準化（キー順・数値表現・Unicode 正規化）の落とし穴を避けられ、エンベロープの中で人が読める。

```
fukanzen-shogi-seal 1
kind finalized
id <正準本文の SHA-256 hex>
witnesses <1|2>
archived_at <ISO8601>
kid <hex16>
```

```
fukanzen-shogi-seal 1
kind disputed
id <暫定 UUID>
text_a <証言 A の SHA-256 hex>
text_b <証言 B の SHA-256 hex>
archived_at <ISO8601>
kid <hex16>
```

エンベロープはこうなる（既存フィールドは**一切変えない**・`seal` を足すだけ＝加算的）:

```json
{
  "finalized": true,
  "text": "…正準本文…",
  "archived_at": "2026-08-22T…Z",
  "witnesses": 2,
  "seal": {
    "alg": "Ed25519",
    "kid": "3f9a…",
    "statement": "fukanzen-shogi-seal 1\nkind finalized\nid …",
    "sig": "<base64url・64バイト>"
  }
}
```

**`statement` を literal で同梱するのが要**。検証側は「statement のバイト列に対する署名」を検めればよく、JSON から statement を組み直す必要がない（＝組み直しの実装差で検証が割れない）。冗長に見える `archived_at`/`witnesses` の二重掲載はむしろ機能する——**平文フィールドが書き換えられたら statement と食い違って露見する。**

### 2.1 封蝋は envelope から**一方向に導出する**（構造で守る）

二重掲載には落とし穴が裏返しについてくる。`buildFinalizedEnvelope` は**内部で `nowIso()` を呼んで `archived_at` を決めている**（`logic.ts`）。もし statement を組むときに `nowIso()` をもう一度呼べば、両者は数ミリ秒ずれる。すると検証側は `archived_at` の食い違いを見て——**`tampered`（改竄の疑い）と報告する**。間欠的で、無言で、しかも最も紛らわしい顔をした偽陽性になる。

これを「実装者が気をつける」で守ってはならない。**構造で守る**:

```
封蝋なしの envelope を作る（archived_at はここで一度だけ確定）
        ↓
その envelope オブジェクト「から」statement を導出する
        ↓
署名して seal を付けた envelope を返す
```

すなわち `sealEnvelope(envelope, key) → envelope`（**一方向の合成**）。statement は envelope の実フィールドを読んで組み立てるので、両者が食い違う経路が存在しない。`witnesses` の二重掲載も同じ理屈で自動的に整合する。

> **原則**: 封蝋の入力は「これから綴じる envelope そのもの」であり、envelope を組むのに使った材料ではない。時刻・乱数・ハッシュを**二度生成する経路を作らない**。

## 3. 鍵（Secret に置き、公開鍵は誰でも取れる場所へ）

- **秘密鍵**: Worker Secret `RECORDER_SIGNING_KEY`（Ed25519 秘密鍵の **JWK JSON 文字列**）。JWK は自己記述的で、`exportKey("jwk")`↔`importKey("jwk")` が往復する。
- **公開鍵**: Ed25519 の秘密鍵 JWK は公開鍵成分 `x` を内包するので、**別 Secret を持たずに導出できる**。
- **`kid`**: raw 公開鍵（32 バイト）の SHA-256 の先頭 16 hex。
- **鍵の import は `logic.ts` のモジュールレベルで memo する**（DO インスタンスごとではない）。Seal-2（`room.ts`）と Seal-3（`index.ts`）は同じ Worker スクリプトで、**同じ鍵を両方が要る**。モジュールレベルなら経路が一本で済む。`importKey` は非同期なので **Promise を memo** すること（並行綴じで二重 import しない）。memo のキーは Secret 文字列そのもの（値が変われば作り直される）。
- **公開口**: `GET /recorder/keys` → `{ "keys": [ { "kid", "alg": "Ed25519", "public_key": "<base64url raw 32B>" } ] }`
  - **配列で返すのは継ぎ目の予約**（プリンシパル設計 §5「継ぎ目だけ空け、作り込まない」）。今は 1 要素。鍵ローテーション（旧鍵で封じた過去局の検証）と、遠い地平の**複数記録係**（二段目 §13）が、この形のまま載る。中身は今は書かない。
- **鍵が無ければ封蝋を省く（degradation）**: Secret 未設定（ローカル `wrangler dev`・Secret 投入前）でも綴じは**従来どおり成立**し、`seal` が無いだけ。**封蝋の失敗が記録の喪失に化けてはならない**——署名は二証人の上に乗る層であって、土台ではない。同じ理由で、署名処理が例外を投げても綴じは続行する（catch して seal なしで綴じ、ログに残す）。

## 4. 段組（Seal-1 → Seal-4・各段独立に検証・難易度つき）

依存は一直線。各段は前段が着地してから、**リポジトリを取り直して**指示書を書く（想像で書かない）。

### Seal-1 — 封蝋の核（`server/src/logic.ts`）｜難易度: **低〜中**

純粋関数と WebCrypto の薄いラッパだけ。DO には触れない。

- `buildSealStatement(kind, fields)` → 行ベース文字列（**純粋**・§2 の書式）
- `kidFromRawPublicKey(raw)` → hex16
- `toBase64Url(bytes)` → string ／ `fromBase64Url(s)` → Uint8Array
- `loadRecorderKey(env)` → `{ privateKey, kid, rawPublicKey } | null`（Secret 未設定なら `null`・§3 のモジュール memo つき）
- **`sealEnvelope(envelope, key)` → envelope**（§2.1 の一方向合成。**このアークの要の関数**）
- `verifySeal(rawPublicKey, seal)` → boolean

**base64url は指示書で書き方を確定させる**（Workers に組み込みが無い）。`btoa` ＋ `+/=` 置換で、Sonnet に発明させない。署名は 64 バイト固定なので `String.fromCharCode(...)` のスタック問題は起きないが、書き方は決めておく。

**テスト**（`server/test/logic.test.ts`・workerd 上なので `crypto.subtle` が使える）: statement のバイト固定（golden）／`sealEnvelope` の往復（封じて検証が通る）／**`sealEnvelope` が envelope の `archived_at` をそのまま使うこと**（§2.1 の回帰固定）／改竄した statement が検証に落ちる／`kid` の決定性／鍵なしで `null`。

> **難易度が低〜中である理由**: 副作用が無く、workerd 上で完結する。**Ed25519 が workerd で動くことは実測確認済み**（`generateKey`/`sign`/`verify`、raw 公開鍵 32B、JWK・pkcs8 からの import、署名は決定的）。Sonnet が迷う余地は書式の一字一句と base64url だけなので、**指示書は statement の golden 文字列と base64url の実装を実例で書き下すこと**。

### Seal-2 — 封蝋を押す（`server/src/room.ts`）｜難易度: **中**｜**このアークの本体**

- `Env` に `RECORDER_SIGNING_KEY?: string` を足す。
- `_archiveFinalized` / `_archiveDisputed` が、**envelope を組んだ後に `sealEnvelope` を通してから** KV へ put する（§2.1）。`buildFinalizedEnvelope`/`buildDisputedEnvelope` のシグネチャは**変えなくてよい**——一方向合成なので後段で足せる。
- **disputed のハッシュは再計算しない**: `evaluateTestimonies` が既に `verdict.idA`/`idB` を持っているのに、現状 `_archiveDisputed([a.text, b.text])` へ渡すとき捨てている（`room.ts` の証言評決部）。これを `_archiveDisputed` へ流し、SHA-256 を二度計算しない。
- **`_archiveFragment` は対象外**（ランダム UUID で content-address されておらず、封じる意味が薄い。§7 の申し送りへ）。
- 署名失敗は catch して seal なしで綴じ、`this.log` に残す（§3 の degradation）。

**触らない境界（明示）**: 招待ゲート（`recording`）・「綴じてから拭く」・二証人評決（`evaluateTestimonies`）・`archived` フラグの立て方には**一切触れない**。封蝋は put の直前に一層かぶせるだけ。

**テスト**: 鍵ありで `seal` が乗り検証が通る／鍵なしで従来どおりの envelope（`seal` 無し）／disputed にも乗る／`witnesses:1` 経路にも乗る／**平文 `witnesses`・`archived_at` を書き換えると statement と食い違う**ことを検証側で検知できる。

> **難易度が中である理由**: DO の状態・失敗経路が絡む。ただし変更点は綴じの 2 関数に閉じており、既存の綴じ判断には触れない。指示書はこの「触らない境界」を明示すること。

### Seal-3 — 鍵の公開口と CORS（`server/src/index.ts`）｜難易度: **低〜中**

- `GET /recorder/keys` を `/archive/:id`・`/watch/:token` と同じ層に足す。DO を介さない。
- 鍵未設定なら `{ "keys": [] }`（404 ではない——「記録係は居るが今は封をしていない」を表す）。
- キャッシュヘッダを付ける（公開鍵は不変）。
- **CORS を足す（この段の必須作業）**——`/recorder/keys` と **既存の `/archive/:id` の両方**に `Access-Control-Allow-Origin: *`。

**なぜ CORS が要るか**: web は `fukanzen-shogi.pages.dev`、Worker は `fukanzen-shogi-ws.tokuhira.workers.dev` で**別オリジン**。今まで問題にならなかったのは、web が `/archive/:id` を**リンクとして開くだけ**（トップレベル遷移＝CORS 不要）だったから。Seal-4 は初めてこれを `fetch()` する。**本番実測で `access-control-allow-origin` は無く、`OPTIONS` は 404**（2026-08-22 確認）。単純 GET・カスタムリクエストヘッダ無しなら preflight は不要なので、**GET 応答にヘッダを足すだけで足りる**（`OPTIONS` ハンドラは作らない＝過ぎたるは及ばざる）。

**`*` は妥協ではなく正しい選択**: 書庫は誰でも `curl` できる公開データとして設計されている（版図「公開情報は対等、綴じ込みだけが特権」）。`*` はその設計を正直に表明するだけで、Pages のプレビュー配備がランダムなサブドメインを取ることにも耐える。

**テスト**: 鍵ありで 1 件・`kid` が Seal-1 と一致／鍵なしで空配列／**`/archive/:id` の CORS ヘッダ**（既存エンドポイントに触るので回帰テスト必須）／既存ルーティング（`/archive/:id`・`/watch/:token`・`/room/:key`）が回帰しない。

> **難易度が低〜中である理由**: ルーティング 1 本の加算自体は易しいが、**既存の `/archive/:id` に触る**ので回帰リスクがある。そして**この段まで来て初めて封蝋が検証可能になる**（Seal-1・2 だけでは誰も確かめられない）ので、ここまでを一区切りとしてデプロイする。

### Seal-4 — 検証を目で見せる（`web/`）｜難易度: **中**｜*別段扱いにしてよい*

- **純粋部**を `web/` の純粋モジュールへ（既存の `reducers.js`・`view-model.js` の作法に倣い、**crypto は注入**して node の vitest で回せる形に）:
  - `sealVerdict(envelope, keys, {sha256, verify})` → `'unsealed' | 'verified' | 'tampered' | 'unsupported' | 'unknown_key'`
  - 判定順: `seal` 無し→`unsealed` ／ `kid` が `keys` に無い→`unknown_key` ／ statement の `id` ≠ sha256(text) か平文フィールドと食い違い→`tampered` ／ 署名検証が落ちる→`tampered` ／ 通る→`verified`。
- **殻**（board.js 側）: `archived{id}` を受けたら `/archive/:id` と `/recorder/keys` を fetch し、判定を `recordStatusText` の隣に出す。
- **これはプロジェクト初の `fetch()`**（`board.js`/`online.js` とも現状 0 件。wasm グルーが同一オリジンで `.wasm` を取るのみ）。**踏襲できる既存パターンが無い**ので、指示書側で失敗時フォールバック（ネットワークエラー・404・JSON パース失敗）の挙動を確定させること。
- **`unsupported` を `tampered` と混同しない**——Ed25519 の WebCrypto 対応は Chrome 137+（2025-05）・Firefox 129+（2024-08）・Safari 17+ で、主要ブラウザは出揃っているが古い環境では `importKey` が投げる。「この環境では検証できません」と「改竄の疑い」は**全く違う知らせ**なので、状態を分けて文言も分ける。
- **既存アーカイブは `unsealed`**（封蝋導入前に綴じた記録）。失敗ではない。

**テスト**: `web/test/` に純粋関数の table テスト（5 状態を尽くす）。crypto 注入なのでビルドレス維持。

> **難易度が中である理由**: 純粋部は素直だが、殻の fetch・失敗時のフォールバック・文言の出し分けが絡む。**指示書は 5 状態それぞれの表示文言を確定させてから渡すこと**（Sonnet に文言を考えさせない）。

### 4.1 なぜ `archived` メッセージに `seal` を相乗りさせないか

「`archived{id, seal}` にすれば Seal-4 の fetch が一回減る」は成り立つが、**採らない**。理由は二つ:

1. ワイヤ語彙が増え、「PROTOCOL 5 据え置き」が崩れる（本アークの加算性・§5）。
2. より本質的に——**サーバの自己申告を検証するのは、保存された現物を取りに行くより弱い**。封蝋の値打ちは「書庫を運営する者の言葉を信じずに確かめられる」ことにある（§0.1）。第三者が後日やるのと同じ経路を、web も通るべき。

## 5. 版の刻み

- **RULE 0.7・PROTOCOL 5・アーカイブ書式版 1 はすべて据え置き。** 封蝋はエンベロープ層で、中身（正準本文）にもワイヤ語彙にも触れない。TUI は無関係。
- **封蝋書式は自前の版を持つ**（`fukanzen-shogi-seal 1`）。エンベロープ層の版はアーカイブ書式版とは別勘定——中身が変わらないのに書式版を上げると、既存棋譜の互換性判断が濁る。
- **配布版（TUI）は据え置き**。Seal-1〜3 はサーバ完結で、配布物に何も入らない。
- **web `?v=` は Seal-4 で前進**。
- **デプロイは二段**: Seal-3 まで着地で `wrangler deploy`＋`wrangler secret put RECORDER_SIGNING_KEY`、Seal-4 で `wrangler pages deploy`。`git push` だけでは本番に反映されない。

## 6. このアークの後に来るもの（順序の理由）

次は **AI 参画**——principal としての AI（版図 §2.2 Named × AI）を、Cloudflare AI Gateway 経由の低コストモデルで立ち上げ、Claude との本格対局への地ならしとする。封蝋を先に置くのは、**AI が量産する棋譜が「確かに綴じられたまま」であることを、最初のログから保証するため**。器を先に、水を後に。

## 7. 非ゴールと申し送り

- **fragment envelope の封蝋** — content-address されていない（ランダム UUID）ので封じる意味が薄い。必要が生じたら。
- **鍵ローテーション** — `/recorder/keys` の配列形で**器だけ空けた**。実際の鍵の入れ替え手順・旧鍵の保持は書かない。
- **複数記録係** — 同上。配列がその土台になる（二段目 §13・版図の遠い地平）。**§0.1 の (b) を塞ぐのは最終的にここ。**
- **削除への対処** — 封蝋は削除を検知しない（§0.1 (a)）。書庫の一覧（バックログ §A）が入れば「あったはずのものが無い」に気づく道が開くが、本アークでは触らない。
- **対局者各々の署名** — 淀川 §1.4 が**保留と明記**した論点。触らない。
- **principal による帰属** — 席は匿名 `-` のまま。封蝋は帰属に及ばない（§1）。次アーク（AI 参画）で動く。
- **書庫の一覧・鑑賞 UI** — バックログ §A のまま。

## 不変の原則（本アークが守るもの）

1. **封じるのは中身の完全性だけ**（淀川 §1.4）。帰属・consent・裁定には及ばない。記録係は自分が観察した事実についてのみ証言する。
2. **審判なし**（二段目 §14-2）。disputed の封蝋は受領の事実であって、優劣の宣告ではない。
3. **署名は二証人の上に乗る層で、土台ではない**。鍵が無くても・署名が失敗しても、綴じは従来どおり成立する。**封蝋の失敗が記録の喪失に化けない。** そして封蝋は二証人・複数記録係を置き換えない（§0.1）。
4. **加算的**。既存 envelope のフィールドを変えず `seal` を足すだけ。既存アーカイブは `unsealed` として読め続ける。RULE・PROTOCOL・アーカイブ書式版は据え置き。
5. **正準化は行ベース**（engine のアーカイブ書式に倣う）。JSON 正準化に依存しない。`statement` は literal で同梱し、検証側に組み直させない。
6. **封蝋は envelope から一方向に導出する**（§2.1）。時刻・乱数・ハッシュを二度生成する経路を作らない。規律でなく構造で守る。
7. **検証できない署名に価値はない**。公開鍵の公開口と CORS（Seal-3）までを一区切りとし、目で見える検証（Seal-4）まで届かせる。
8. **「検証不可」と「改竄」を混同しない**。環境の制約と、記録への疑いは、全く違う知らせ。
9. **継ぎ目だけ空け、作り込まない**（プリンシパル設計 §5）。鍵は配列で返すが、ローテーションも複数記録係も今は書かない。
