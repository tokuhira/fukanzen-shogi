# 不完全将棋 記録係三段目（封蝋）アーク 総括（Seal-1〜Seal-4）

*この文書は、記録係二段目が非ゴールとして申し送った「記録係署名＝完全性の封蝋」（二段目 §13）を据えた一連の実装（Seal-1〜4、2026-08-22、本番デプロイ済み）の総括である。段ごとの詳細は各実装指示書（`archive/implementation/recorder-seal/`）にあり、設計の錨は同ディレクトリの『概観と段組』。ここは道のり・確立した設計・確定した判断・残された次の畝を粗く俯瞰する地図。なお本アークは、上位設計（概観・全段の実装指示書・レビュー）を Claude Code 内 Opus が担い、実装を別セッションが担う分業が四段続けて回った初めての例でもある。*

## 0. このアークが始まった地点と、達成したこと

**始点**: 記録は「誰でも書ける JSON」だった。二証人（対局者二人の証言の内容ハッシュ一致）は**対局者どうしの食い違い**を検知するが、**綴じた後の改竄**は検知しない。書庫を運営する者が後から書き換えても、第三者にはそれを確かめる術がなかった。

**終点（現在）**: 記録係が Ed25519 で封蝋を押し、公開鍵を誰でも取れる場所に置き、web が**保存された現物を取りに行って**検証して人に見せる。実対局で端から端まで動作を確認済み:

```
綴じる側:  archived finalized id=64fb008d… witnesses=2 sealed=true
読む側:    封蝋を確認しました（綴じられた時のままです）
第三者:    verified（デプロイ済みモジュールで独立検証・改竄させれば tampered）
```

RULE 0.7・PROTOCOL 5・アーカイブ書式版 1・配布 v0.13.0 はすべて据え置き（封蝋はエンベロープ層で、中身にもワイヤ語彙にも触れない）。前進したのは web `?v=` 0.13.0→0.13.1 と、新設した封蝋書式版 `fukanzen-shogi-seal 1` のみ。server テスト 20→**62 件**、web テスト 132→**154 件**。

**確立した設計パターン**:
- **封蝋は envelope から一方向に導出する**（概観 §2.1）。時刻・乱数・ハッシュを二度生成する経路を作らない。規律ではなく構造で守る。
- **封じるのは中身の完全性だけ**（淀川 §1.4）。帰属・consent・裁定には及ばない。記録係は自分が観察した事実についてのみ証言する。
- **「検証不可」と「改竄」を混同しない**。環境の非対応・未知の alg・未来の書式版・鍵材の破損・封蝋の不在——いずれも記録への疑いではなく、文言まで分ける。
- **degradation は綴じを守る方向へ倒す**。鍵が無くても壊れていても、綴じは従来どおり成立し `seal` が無いだけ。**封蝋の失敗が記録の喪失に化けない。**
- **検証はサーバの言葉を信じない**。`archived` メッセージに封蝋を相乗りさせず、web も第三者が後日辿るのと同じ経路（`GET /archive/:id`）を通る。

## 1. 機構と API（Seal-1〜4 で新設）

| 場所 | もの | 役割 |
|---|---|---|
| `server/src/logic.ts` | `buildSealStatement(subject, archivedAt, kid)` | 行ベースの署名対象（engine のアーカイブ書式に倣う・JSON 正準化に依存しない） |
| 〃 | `sealFinalized(env, id, key)` / `sealDisputed(env, id, hashes, key)` | **一方向合成**。`archived_at`・`witnesses` は envelope からしか読まない |
| 〃 | `loadRecorderKey(env)` | Secret 未設定は `null`（正常）、壊れていれば throw（異常）。モジュールレベルで Promise を memo |
| 〃 | `verifySeal(rawPublicKey, seal)` | 署名の正しさ**だけ**を見る。内容の突き合わせは上位の仕事 |
| `server/src/room.ts` | `_archiveFinalized` / `_archiveDisputed` | 鍵の読み込みごと try に入れ、**put は try の外**。封蝋の失敗が put へ到達することを妨げない |
| `server/src/index.ts` | `GET /recorder/keys` | 公開鍵を配列で返す（鍵ローテーション・複数記録係の**継ぎ目の予約**）。鍵が無ければ `{ "keys": [] }` の 200 |
| 〃 | `PUBLIC_CORS` | `/recorder/keys` と `/archive/:id` の 200・**404 の両方**に `Access-Control-Allow-Origin: *` |
| `web/seal-verify.js` | `sealVerdict(id, envelope, keys, subtle?)` | 五判定（`verified`/`unsealed`/`tampered`/`unknown_key`/`unsupported`）。純粋——DOM も fetch も知らない |
| `web/board.js` | `verifyArchivedSeal(id)` | 殻。`/archive/:id` と `/recorder/keys` を取りに行く。**プロジェクト初のクロスオリジン fetch** |

## 2. 段ごとの道のり

**Seal-1（封蝋の核・`logic.ts`）**: 純粋関数と WebCrypto の薄いラッパのみ。**まだ誰も呼ばない**ので挙動は変わらず、書式と test vector をここで固めた。golden 値は指示書を書く前に workerd 上で実測生成し、指示書のコードを写したプローブで再現を確認してからコミット。テスト 20→43 件。

**Seal-2（封蝋を押す・`room.ts`）**: 綴じの 2 関数の put 直前に一層かぶせるだけ。招待ゲート・「綴じてから拭く」・二証人評決・`archived` の立て方には触れない。**このプロジェクト初の DO テスト**（`runInDurableObject` で内部メソッドを直接呼び、Secret は `env` の実行時書き換えで注入）。テスト 43→53 件。

**Seal-3（鍵の公開口と CORS・`index.ts`）**: ルーティング一本と CORS ヘッダ。実装は軽く**段取りが本体**——本番鍵の生成・`wrangler secret put`・`wrangler deploy`・4 種の本番確認。`SELF.fetch` で Worker を統合テスト。テスト 53→62 件。ここまでで初めて封蝋が検証可能になる。

**Seal-4（検証表示・`web/`）**: 判定は純粋モジュール、fetch は殻。表示は `record-info-row` に一行足すだけ（恒常的な UI 面は別アークの仕事）。テスト 132→154 件。web `?v=` 0.13.1。

## 3. 実測で見つかった罠（このアークの実質的な収穫）

いずれも**書く前・出す前に手を動かして**見つかった。読んでいるだけでは出てこなかった。

1. **`archived_at` の二重生成が偽の「改竄」を生む**（Seal-1 前）— `buildFinalizedEnvelope` は内部で `nowIso()` を呼ぶ。statement 用にもう一度呼べば数ミリ秒ずれ、検証側が `tampered` と報告する。間欠的・無言・最も紛らわしい顔をした偽陽性。→ **一方向合成**で経路自体を消した（概観 §2.1）。

2. **CORS が無く Seal-4 が成立しない**（Seal-1 前）— web は Pages、Worker は workers.dev で別オリジン。リンクで開くだけ（トップレベル遷移）なら不要だったが、`fetch()` には要る。本番実測でヘッダ無しを確認。**404 にも要る**——無いと「記録が無い」と「ネットワークが死んだ」を区別できない（CORS ヘッダの無い応答は status に関係なく fetch が reject するため）。

3. **node と workerd で Ed25519 の JWK が食い違う**（Seal-3 前）— node は `alg: "Ed25519"` を書くが workerd は RFC 8037 の `alg: "EdDSA"` を期待して**拒否する**。気づかず `secret put` すると、Seal-2 は仕様どおり封蝋なしで綴じ続けるため「鍵を入れたのに何も封印されない」がログを見ない限り続く。**degradation が正しく効いているぶん、かえって静かに壊れる。**→ `kty`/`crv`/`x`/`d` だけの最小形を生成する。

4. **歯の無いテストが二度**（Seal-1・Seal-2 のレビュー）— §5 に詳述。

5. **`curl -sI` は HEAD なので 404 になる**（Seal-3 デプロイ時）— ハンドラが `method === "GET"` で判定しているため。私が指示書に書いた確認コマンド自身が誤っていた。実行して初めて分かる類。

6. **鍵材の破損が `unsupported` に化ける**（Seal-4 前）— プロトタイプ検証中にフィクスチャの公開鍵へ全角が一文字紛れ、「この環境では検証できません」と表示された。デコードと `importKey` を別々に受け、`unknown_key` と分離した。

## 4. 確定した判断（再燃防止・re-litigate しない）

- **`archived` メッセージに `seal` を相乗りさせない。** ワイヤ語彙が増えて PROTOCOL 据え置きが崩れる上、サーバの自己申告を検証するのは保存された現物を取りに行くより弱い。
- **`OPTIONS` ハンドラを作らない。** 単純 GET・カスタムヘッダ無しなら preflight は飛ばない。裏返しに、**Seal-4 の fetch に独自ヘッダを付けない**ことがこの判断を支えている。
- **`Access-Control-Allow-Origin: *` は妥協ではない。** 書庫も公開鍵も誰でも `curl` できる公開データとして設計されている（版図「公開情報は対等、綴じ込みだけが特権」）。オリジンを絞るのは、守るものが無いのに鍵をかけるのと同じ。
- **`_archiveFragment` は封蝋の対象外。** content-address されていない（ランダム UUID）ので封じる意味が薄い。
- **公開鍵は配列で返す。** 今は 1 要素。鍵ローテーションと複数記録係が、この形のまま載る（プリンシパル設計 §5「継ぎ目だけ空け、作り込まない」）。
- **`unsealed` は失敗ではない。** 封蝋導入前の記録が本番に 25 件ある。事実として報告する。

## 5. このアークで効いた流儀（次の Opus・実装者へ）

**テストの歯はバグ注入で確かめる。読むだけでは見抜けない。**

三段すべてで穴が出た:

- **Seal-1**: 「`archived_at` 回帰固定」を名乗るテストが、その守るべきバグを **200/200 ですり抜けた**。`toISOString()` はミリ秒解像度で、I/O を挟まない二度の生成は必ず同じミリ秒に落ちるから。「今」ではありえない sentinel（1999-01-01）へ変えて解決。
- **Seal-2**: 9 件揃っていたのに「statement の `id` が本文の SHA-256 と一致する」＝**封蝋の中心的な約束**を誰も見ていなかった。誤った id を注入したら 9 件全通過。
- **Seal-3・Seal-4**: 実装者が自ら注入検証を行い、報告どおり歯があることをレビューでも再確認。

手順は毎回同じ——(1) 実装を一時的に壊す、(2) 対象テストが落ちるか実測、(3) `git checkout` で復元、(4) 復元をテスト再実行で確認、(5) プローブを削除。

**指示書には実測で確かめた値だけを書く。** golden 文字列・署名・test vector は、指示書のコードをそのまま写したプローブで再現を確認してからコミットする。転記ミスは実装者を詰ませる。Seal-2〜4 では**指示書のコードを実際に現物へ当てて走らせ**、パスを確認してから復元した。

**設計文書ごとにコミットを刻む。** 概観→コミット、各段の指示書→コミット、実装→コミット。実装前の状態が履歴に残り、どこまでが合意でどこからが実装かが後から読める。

**視点の近い実装者は盲点も共有する。** Seal-4 は同じ Opus が実装したため、指示書の誤りは素通りしうる立場だった。実際には実装者が**指示書に無い確認**（CI と同じ Node 20 での検証）を足して私の穴を埋めた——私は Node 24 でしか試していなかった。レビュー側は「指示書どおりか」ではなく「**指示書が正しかったか**」を見る必要がある。

## 6. 既知の限界と次の畝

**封蝋が塞がない穴**（概観 §0.1・過大な期待を書かない）:

- **削除** — 記録ごと消されれば封蝋は何も言わない。書庫の一覧（バックログ §A）が入れば「あったはずのものが無い」に気づく道が開く。
- **鍵を持つ運営者による捏造** — 鍵があればありもしない対局を封じられる。第一の防波堤は**二証人**、究極的には**複数記録係の突き合わせ**（版図の遠い地平）。封蝋はそれを置き換えず、上に重ねる一層。

**開いたまま残るもの**:

- 断片（fragment）の封蝋／鍵ローテーションの実運用（器だけ空けた）／複数記録係
- 対局者各々の署名（淀川 §1.4 が保留と明記・触っていない）
- principal による帰属（席は匿名 `-` のまま。封蝋は帰属に及ばない）
- TUI クラウド対局の記録係対応（招待受諾・証言送出が未実装）

**このアークの実対局で表面化し、バックログへ落としたもの**:

- **ゾンビ席で `room_full`**（§D）— ソケットが非正常に切れると DO が席を握り続ける。実測で約 97 秒、その間ずっと正当な再接続が弾かれた。**AI で量産する前に効いてくる。**
- **web UI の面が盤だけ**（§C）— 封蝋の検証表示を置く場所が「盤の脇の一行」しかなかった。招待トグル・席の状態・書庫の導線も同じ制約に当たっている。
- **カスタムドメインのキャッシュと `?v=` の穴**（§C）— `tokuhira.net` だけ JS が 4 時間キャッシュされ、ES モジュールの import は無版なので新旧が混ざりうる。

**次アークは AI 参画**（バックログ §E）。器（封蝋）が整ったので水を流せる——AI が量産する棋譜が、最初のログから改竄検知可能な形で綴じられる。「器を先に、水を後に」の意図はここで果たされる。
